## 2. Behavioral Differences Between Warmup and Replay

### DIFF-1: Compilation happens DURING the frozen warmup (capture)

**File**: `NativeDynamicShapePlan.cpp` lines 1262-1265, 1446-1448

- During the **frozen warmup** (executeCount_=0), `phaseCompile()` is **skipped** at line 1262 because of the guard `!(shapesFrozen_ && executeCount_ == 0)`.
- Instead, `phaseCompile()` fires at line 1446 when `executeCount_ == 1` (after the warmup completes, before execute() returns).
- This means the **first frozen replay** (executeCount_=1) has freshly compiled Triton modules but **the capture happened before compilation**.

**Risk**: The CUDA graph captured during warmup contains native op nodes (cuBLAS, etc.), NOT Triton-compiled kernels. The Triton compilation happens AFTER capture. If the Triton graph backend is supposed to replace native ops, the captured CUDA graph may contain the wrong nodes.

### DIFF-2: `outputSlots_` is zeroed on first frozen warmup, populated on replay

**File**: `NativeDynamicShapePlan.cpp` lines 1166-1176, `NativePlanCompiler.cpp` line 545

- At plan creation, `outputSlots_` is `memset` to all zeros.
- During the frozen warmup (executeCount_=0), slots are allocated and populated by `executeSegmentSlotBySlot()`.
- During replay (executeCount_>=1), `outputSlots_` contains the **same NDArray pointers** from warmup (arrays persist).

**Critical**: The `frozenConstantSlot()` fast path in `executeSlot()` (line 992) checks `shapesFrozen_ && executeCount_ > 0`. On warmup, this is **false** (executeCount_=0), so constant-producing slots execute normally. On replay, this is **true**, so these slots are **skipped entirely** — their output buffers are reused without recomputation.

**Risk**: If a slot is incorrectly classified as `frozenConstantSlot()`, its device buffer will contain **stale data** from warmup that never gets updated during replay.

### DIFF-3: `tl_graphExecutionActive` changes memory management behavior

**File**: `NativeDynamicShapePlan_cudagraph.cu` line 519, `DataBuffer.cu` lines 45, 63, 78, 1242, 1259, 1318, 1411, 1425, 1542

During CUDA graph capture:
- `tl_graphExecutionActive = true` (line 519 of cudagraph.cu)
- `syncToDevice()` becomes async (line 78 of NDArray_core.cu) — **no cudaStreamSynchronize**
- `syncFromDevice()` / `readSpecial()` skip sync (line 63 of NDArray_core.cu)
- Memory frees are suppressed → `cudaFreeAsync` instead of `cudaFree` (line 45 of CudaPointerDeallocator.cu)
- Cross-device memsets are skipped (line 1428 of DataBuffer.cu)
- Buffer migration to device is skipped (line 1542 of DataBuffer.cu)

During replay:
- `tl_graphExecutionActive = false` — all syncs and frees behave normally

**Critical risk**: During capture, `syncToDevice()` is async. If any input data hasn't been written to the device buffer before the capture records the H2D memcpy node, the graph will capture **stale/zero data**. During replay, the same async path is NOT used, but the graph already baked in the wrong addresses.

### DIFF-4: `refreshArgTablesForReplay` only runs for Triton backends

**File**: `NativeDynamicShapePlan_cudagraph.cu` lines 287-293, `TritonGraphBackend_kernel.cu` lines 1012-1155

The `refreshArgTablesForReplay()` call is **inside a `#if HAVE_TRITON` block** and only executes when:
1. The segment has a TritonGraphBackend
2. The segment uses indirect arg passing

For **pure CUDA graph** segments (non-Triton, using native ops like cuBLAS), `refreshArgTablesForReplay` is **never called**. The baked-in CUDA graph kernel nodes have **hardcoded buffer pointers** from capture time.

**Critical**: The replay path at line 280-285 does sync external inputs to device:
```cpp

  for (int ei = 0; ei < numExt; ei++) {
    if (externalArrays[ei] != nullptr) {
      externalArrays[ei]->syncToDevice();
    }
  }
}
```
But this sync happens **before** the `refreshArgTablesForReplay` call. If `replayInputsStable` is false (addresses drifted), the code falls through to cleanup and slot-by-slot execution (line 326-330).

### DIFF-5: `argTableStable` optimization skips expensive checks

**File**: `NativeDynamicShapePlan_gpubackend.cpp` line 2708

### DIFF-6: `phaseFreeze` resets ALL segment state

**File**: `NativeDynamicShapePlan.cpp` lines 1644-1711

When `phaseFreeze()` is called (transition from unfrozen to frozen):

This means every time `setShapesFrozen(true)` is called, the plan starts a **brand new** warmup→compile→replay cycle.

### DIFF-8: `executeSegmentSlotBySlot` runs differently during capture vs. replay

**File**: `NativeDynamicShapePlan_segments.cpp` lines 795-1043, `NativeDynamicShapePlan_slotexec.cpp` lines 878+

During warmup/capture, `executeSegmentSlotBySlot()` executes each slot's native op. The `frozenContextReady()` fast path in `executeSlot()` (line 1185) is **only taken when `slot.state_ >= FROZEN`**. During warmup, slot states start at `WARMUP` or `SHAPE_CACHED`, so the frozen fast path is NOT taken.

During replay, slot states are `FROZEN` or `FROZEN_CONSTANT`, so:
- View-producing ops create views from cached shape info instead of executing native ops
- Constant-producing slots are skipped entirely
- Input resolution reads from `outputSlots_` which persist from warmup

**Risk**: The restore at line 378 (`std::memcpy(outputSlots_, preWarmupOutputSlots, ...)`) means the captured graph references the **old** slot arrays, not the ones produced by the warmup execution. If the warmup execution allocated NEW arrays (different addresses), the graph captures stale pointers.

## 3. Most Likely Culprits for Garbage VLM Decode Output

### HIGH RISK: Frozen Constant Slot Misclassification (DIFF-2 + DIFF-8)

If a slot that **produces dynamic data** (e.g., attention output that changes per decode step) is incorrectly flagged as `frozenConstantSlot()`, it will be skipped during replay. The device buffer will contain stale data from the warmup (prefill) execution, causing garbage output downstream.

**Where to look**: `detectFrozenConstants()` in NativeDynamicShapePlan.cpp — the logic that marks slots as FROZEN_CONSTANT.

### HIGH RISK: Stale Triton Arg Tables on First Replay (DIFF-1 + DIFF-4)

Triton compilation happens AFTER the frozen warmup (capture). The captured CUDA graph contains native op nodes. On the first replay, `refreshArgTablesForReplay` updates Triton arg tables, but the CUDA graph still has native ops with baked-in pointers. If the Triton-compiled version of the segment is supposed to **replace** native ops but the captured graph still contains the native versions, the replay executes the wrong code path.

**Where to look**: `executeSegmentWithGpuGraph()` in `NativeDynamicShapePlan_gpubackend.cpp` — specifically the dispatch between Triton replay and CUDA graph replay.

### MEDIUM RISK: External Input Not Synced Before Replay (DIFF-10)

If `computeSegmentInputAddrKey()` returns a key that matches the captured key but the **data** in those buffers has changed (same addresses, different content), the `syncToDevice()` call runs but the Triton arg tables may not be refreshed if `argTableStable` was set from a prior step.

### MEDIUM RISK: `tl_graphExecutionActive` Side Effects During Capture (DIFF-3)

During capture, `syncToDevice()` is async. If the host buffer for an external input hasn't been fully written before capture records the H2D memcpy, the graph captures a memcpy of incomplete data. This would produce consistent garbage on every replay.

4. **Compare argmax of warmup output vs first replay output**: If they differ, the bug is in the warmup→replay transition. If they match but output is still garbage, the bug is earlier (in the warmup itself or in the Java-side input preparation).
