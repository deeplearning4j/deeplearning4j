# KV Cache Position Desync Analysis

## 1. Architecture Summary: Two Position Counters

| Layer | Variable | Location | Purpose |
|-------|----------|----------|---------|
| **Java** | `cachePos` (local var in decode loop) / `kvCacheManager.cachePosition` | `StaticKvCacheDecodeLoop.java` + `StaticKvCacheManager.java` | Tracks how many tokens have been written into the static KV buffers. Used for building position_ids, attention masks, and configuring C++ scatter. |
| **C++** | `kvCachePosition_` | `NativeDynamicShapePlan` (member field) | The position where the C++ KV scatter kernel writes the *next* token's KV data into the pre-allocated static buffers. |

The two counters are **completely independent** — there is no automatic synchronization mechanism between them after initial configuration.

## 3. Identified Desync Scenarios

### 🔴 CRITICAL BUG #1: `releaseGpuIntermediates(true)` resets C++ position but NOT Java position

**File**: `NativeDynamicShapePlan.cpp`, line 2239  
**File**: `DynamicShapePlanExecutor.java`, lines 1640-1662  
**File**: `StaticKvCacheDecodeLoop.java` — Java `cachePos` is **never** reset here.

**Scenario**: If `resetForNextPageDecode()` is called between pages (VLM multi-page decoding):

1. C++ `kvCachePosition_` is reset to **0** via JNI call to `releaseGpuIntermediates(nativePlanHandle, true)`
2. Java-side in `releaseGpuIntermediates(true)`:
   - `savedKvCurrentPos = 0` (line 1655)
   - `kvCacheRetentionConfigured = false` (line 1656)
3. But the **`StaticKvCacheManager.cachePosition` is NEVER reset**. It still holds the value from the end of the previous page (e.g., 1200).

**Next page decode starts**:
- Java reads `cachePos = kvCacheManager.getCachePosition()` → returns 1200
- Position_ids and attention_mask are built for position 1200
- C++ `kvCachePosition_` is **0** (reset)
- KV scatter writes token 1's KV at position **0** instead of position **1200**
- The model attends to stale KV data from the previous page → **garbage output**

**Impact**: This is the most likely root cause for multi-page VLM decode producing garbage.

| **1** | `releaseGpuIntermediates(true)` resets C++ `kvCachePosition_` to 0 but **does not reset Java `kvCacheManager.cachePosition`** | **CRITICAL** | Multi-page VLM decode using `resetForNextPageDecode()` | Java builds position_ids for position N, C++ scatters at position 0 → model attends to corrupted KV history → **garbage output** |

## 5. Root Cause Assessment

**The primary root cause of garbage VLM decode output is Bug #1**: When transitioning between pages with `resetForNextPageDecode()`:

- C++ `kvCachePosition_` → **0**
- Java `kvCacheManager.cachePosition` → **unchanged** (e.g., 1200 from previous page)
- Java builds `position_ids` = [1200], `attention_mask` at index 1199 = 1
- C++ scatters new KV at position **0** in the static buffers (overwriting the first token's KV)
- The model attends using position 1200 queries against KV data at positions 0..N (corrupted mix of new page data at position 0 and stale old-page data at positions 1..N)

This produces degenerate attention patterns → garbage output with no crash.

## 6. Recommended Fix

In `DynamicShapePlanExecutor.releaseGpuIntermediates(boolean preserveDecodeState)`, the Java-side KV cache manager position must also be reset when `preserveDecodeState=true`. However, the executor doesn't have a reference to the `KvCacheManager`. 

The fix needs to be at the **caller level** in the VLM decode orchestration code. When `resetForNextPageDecode()` is called, the caller must also:
1. Reset `kvCacheManager.cachePosition` to match the new page's prefill length
2. Or ensure a fresh `KvCacheManager` is used for each page

Alternatively, the `resetForNextPageDecode()` API should accept the new page's `cachePosition` as a parameter and propagate it through JNI to the C++ side, ensuring both sides are reset to the same value.
