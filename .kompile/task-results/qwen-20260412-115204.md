## Investigation Summary: DSP Execution Order vs Standard Path

I've completed a thorough investigation of the DSP execution order compared to the standard InferenceSession path. Here are the findings:

### 1. **Slot Order Determination (NativePlanCompiler.cpp)**

**How DSP determines order:**
- The Java `DynamicShapePlanCompiler` receives a `ForwardExecutionDAG` with a pre-computed topological order
- Slot N in DSP = the N-th op in the filtered execution order (skipping VARIABLE_INIT, PLACEHOLDER_SET nodes)
- The native `NativePlanCompiler::compile()` iterates `opNodes` in array order and assigns `stepIdx` sequentially
- **Critical:** The topological sort happens in Java via `ForwardExecutionDAGBuilder.createTopologicalOrder()` (line 462-480)

**How standard path determines order:**
- `ForwardExecutionDAGBuilder.buildForwardDAG()` performs backward traversal from requested outputs
- Uses `findRequiredSubgraph()` to find all producer ops transitively
- Creates topological order via recursive DFS (`topologicalSort()`)

**Key finding:** Both paths use the **same** `ForwardExecutionDAG`, so they should execute ops in the same order **if the DAG is built correctly**.

### 2. **Potential Order Divergence Issues**

**Issue A: Non-deterministic Topological Sort**
- The topological sort in `createTopologicalOrder()` iterates `operationNodes.values()` which is a `HashMap`
- HashMap iteration order is **not guaranteed** to be deterministic across JVM runs or graph builds
- If two ops have no dependencies between them, their relative order depends on HashMap bucket ordering
- **This could cause different slot assignments between recompilations**

**Issue B: Standard path uses `getExecutionOrder()` but may re-traverse DAG differently**
- The standard InferenceSession path in `executeOperations()` traverses the DAG node by node
- If the DAG is rebuilt (cache miss), HashMap ordering could differ

### 3. **Slot Aliasing Investigation**

**Finding:** No slot aliasing found in the compilation code. Each op output gets a unique slot index:
```java
// DynamicShapePlanCompiler.java line 210-214
for (ExecutionNode node : opNodes) {
    for (String outputVar : node.getOutputVariables()) {
        varToOutputSlot.put(outputVar, nextSlotIndex++);
    }
}
```

Each output variable maps to a unique sequential slot. No two ops write to the same slot.

### 4. **slotIsDead_ Logic**

**Finding:** The `slotIsDead_` logic is **correct for non-control-flow graphs**:
- Initialized to all false (`memset` to 0)
- Only modified for control flow ops (Switch, Merge, etc.)
- For transformer layers without CF ops, dead flags remain false
- **However:** If the graph has ANY control flow ops, dead propagation could skip ops incorrectly

**Potential issue:** The dead-slot check at line 960-963 in `NativeDynamicShapePlan_segments.cpp`:
```cpp
if (hasControlFlow_ && slotIsDead_ != nullptr) {
  if (anyInputDead(slot, slotIsDead_, slotIsDeadSize_)) {
    markOutputsDead(slot, slotIsDead_, slotIsDeadSize_);
    stepIdx++;
    continue;  // <-- SKIPS EXECUTION
  }
}
```

If `hasControlFlow_` is set incorrectly (even for graphs without actual CF ops), this could skip ops.

### 5. **attn_mask_reformat Subgraph Caching** ⚠️ **LIKELY CULPRIT**

**Critical finding:** The `attn_mask_reformat` subgraph produces a 4D attention bias that changes each decode step (as `attention_mask` grows). 

**DSP behavior:**
- Compiles the entire graph including `attn_mask_reformat` into a plan
- The subgraph executes as slots in the plan
- **If the attention_mask input changes shape**, the plan may need recompilation
- If shapes are frozen (`shapesFrozen=true`), the plan might reuse stale bias

**Standard path behavior:**
- Recomputes `attn_mask_reformat` every execution via normal DAG traversal
- Always uses current `attention_mask` values

**Divergence scenario:**
1. Layer 0-29: attention_mask is the same (causal mask for same sequence length)
2. DSP computes `attn_mask_reformat` once during first execution
3. If DSP caches the plan and the bias output slot is reused without recomputation
4. **BUT:** The attention_mask should be an external input that changes, forcing recomputation

**More likely issue:** The `attn_mask_reformat` output is consumed by attention ops in multiple layers. If:
- Layer 0's attention uses the reformat output correctly
- Layer 1's attention also uses the **same slot** (if the variable name is shared across layers)
- This would cause layer 1 to use layer 0's bias

### 6. **Most Likely Root Causes**

**Primary suspect: Output slot reuse across transformer layers**

If the ONNX model has 30 transformer layers that share the same variable names (e.g., all use `attn_mask_reformat/Tile/output_0`), but they're **different ops in the graph**, they would get **different slots**. This is correct.

**However**, if the model uses **identity ops** or **view ops** that alias buffers:
- RMS_norm output might be a view of input (shares buffer)
- If DSP doesn't detect this and zeroes the buffer, it corrupts the view

**Secondary suspect: View-capable op zeroing bug**

From `NativePlanCompiler.cpp` line 244-246:
```cpp
slot.flags.needsZeroedOutput = slot.flags.isViewCapableOp ? false
                         : (!hasOpTrait(slot.ident.op, sd::ops::OP_TRAIT_FULLY_WRITING) || isDataDep);
```

If an op is incorrectly marked as view-capable, its output buffer won't be zeroed, and if the buffer was reused from a prior op, it would contain stale data.
