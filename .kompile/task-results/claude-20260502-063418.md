### 1. **CRITICAL — `backfillCachedOutputShapes` early return + shape pre-pass interaction** (slotexec.cpp:62)

**The change:**
```cpp
// NEW — added at line 62:
if (slot.state_ >= NativeSlot::SlotState::SHAPE_CACHED) return;
```

**Why it's dangerous:** The new `phaseShapeInferenceOnly()` pre-pass (NativeDynamicShapePlan.cpp:1883-1897) runs before the first real execution. It sets `slot.state_ = SHAPE_CACHED` and populates `cachedOutputShapes` based on the **prefill** input shapes. Later, during **warmup** (`phaseWarmup`), states are correctly reset to `WARMUP` and `cachedOutputShapes.clear()` is called (line 2985). BUT — the pre-pass also runs when `!shapePrePassDone_ && !shapesFrozen_`, which is TRUE on the first execution of the unfrozen phase (before freeze). The pre-pass populates shape caches from prefill shapes. The early return guard at line 62 then prevents `backfillCachedOutputShapes` from ever updating those shapes if the actual execution produces different output shapes (e.g. different output dtypes after type promotion, or shapes that calculateOutputShape computed differently from the pre-pass). The pre-existing guard `if (!slot.shapeCache.cachedOutputShapes.empty()) return;` was sufficient — the new state-based guard is **redundant AND more aggressive** because `SHAPE_CACHED` persists even after cachedOutputShapes has been repopulated by different values.

**Impact:** Stale shape caches → wrong output array shapes or dtypes → wrong kernel results → accuracy regression. Affects BOTH backends.

### 2. **HIGH — `prezeroSegmentOutputs` skip in frozen steady-state** (segments.cpp:931)

**The change:**
```cpp
// NEW:
if (!(shapesFrozen_ && executeCount_ >= 2)) {
    prezeroSegmentOutputs(seg, stream);
}
```

**Why it's dangerous:** This skips memset-zeroing of output buffers when shapes are frozen and executeCount >= 2. The comment says "ops fully overwrite them" — but this is only true if **every** op in the segment writes to **every element** of its output. Ops that write partial outputs (e.g., scatter, gather, ops with masking, softmax with padding) leave stale values in the unwritten portions. On the first execution after freeze, outputs were correctly zeroed. On subsequent executions, stale data from the previous step persists. This would affect BOTH backends identically since prezero is platform-neutral.

**Impact:** Garbage in unwritten output elements → wrong downstream results → accuracy regression.

### 3. **HIGH — `nativeSlotCallback` with persistent `nativeRangeSegments_`** (segments.cpp:712-737)

**The old code:** Created a stack-allocated `GraphSegment nativeSeg` per native range callback call — fresh every time, `isCapturable=false`, `executionCount=1`.

**The new code:** Uses persistent `nativeRangeSegments_` map entries. Sets `isCapturable=true`, creates a `FunctionalReplayHandle`, and increments `executionCount` across calls. This means the native sub-segments now enter the CPU_FROZEN_REPLAY fast path (line 961-984) after the second execution. The frozen replay path **skips** certain slots (frozen constants, identity ops, fused chain tails) that the old code executed every time. If any of those skipped slots have side effects or if the FunctionalReplayHandle's `executableSlotIndices` list was built during warmup with a different execution pattern than decode, it will skip slots that should execute.

**Impact:** Skipped ops in native sub-segments → missing computation → accuracy regression.

### 4. **MEDIUM — `dynamic_cast` → `static_cast` for FunctionalReplayHandle** (segments.cpp:963, 1499)

**The change:**
```cpp

auto* funcHandle = dynamic_cast<FunctionalReplayHandle*>(seg.exec.replayHandle.get());
// NEW:

```

On CPU, `GraphReplayFactory::create(0)` does return `FunctionalReplayHandle`, so this is safe for the main segment path. **BUT** — on CUDA, `GraphReplayFactory::create(deviceId)` returns `CudaGraphReplayHandle`. If this code ever executes on CUDA (e.g., a segment that fell back to slot-by-slot on CUDA), `static_cast<FunctionalReplayHandle*>` on a `CudaGraphReplayHandle*` is **undefined behavior** — it would reinterpret the wrong object as FunctionalReplayHandle, and `hasExecutableSlotIndices()` could return true with garbage data, leading to skipped ops.

However, for pure CPU execution this is safe. For CUDA, the `shapesFrozen_ && executeCount_ >= 2 && seg.exec.replayHandle->isReady()` guard likely filters it out since CUDA handles would report different ready states.
