## Analysis: Accuracy-Critical Changes in `NativeDynamicShapePlan_slotexec.cpp`

Here are the changes between commit `9bb2680e2b` (last known-good) and the current working tree that could cause output arrays to contain wrong data or zeros. I've ranked them by risk.

### 1. **CRITICAL — Fused chain intermediate slots now get SEPARATE arrays instead of aliases** (lines 2254-2277)

**Old code** (line 1878 in old file):
```cpp
writeOutputSlot(chainOutputSlotIdx, output, "fused-chain-member");
```
All intermediate chain slots pointed to the **same** `output` NDArray as the fused chain head.

**New code** (lines 2261-2270):
```cpp
NDArray* memberOut = outputSlots_[chainOutputSlotIdx];
if (memberOut == nullptr) {
    memberOut = new NDArray(const_cast<LongType*>(outputShapeInfo), true, LaunchContext::defaultContext());
    writeOutputSlot(chainOutputSlotIdx, memberOut, "fused-chain-member-alloc");
}
```
Intermediate chain slots now get their **own newly-allocated arrays**, but these arrays are **never written to by the fused kernel**. The fused kernel `fusedElementwiseChain()` only writes to `output` (the head). These intermediate NDArrays contain **uninitialized memory** (or zeros from initial allocation). Any downstream slot that reads from an intermediate chain slot will see **wrong data or zeros**.

The comment says "The OpenVINO/OneDNN backend re-executes the segment and binds EACH slot's output buffer independently" — but if the CUDA path is active and NOT the OV backend, those intermediate arrays remain unwritten. This is the **most likely cause of the accuracy regression**.

Additionally, the `if (memberOut == nullptr)` guard means on the second+ execution, the stale intermediate array from the first execution persists. If the fused kernel writes different values to `output` on each step, the intermediate slot arrays remain frozen at their initial uninitialized state.

### 3. **HIGH RISK — `isDynamicShape` no longer unconditionally set on shape drift** (lines 1170-1176 in new, replacing old lines 3235)

**Old code:**
```cpp
slot.flags.isDynamicShape = true;  // ALWAYS set on shape drift during warmup
```

**New code:**
```cpp
if (hasDynamicUpstream) {
    slot.flags.isDynamicShape = true;
}
```

If a slot experiences shape drift during prefill→decode transition but `hasDynamicUpstream` returns `false` (because the BFS doesn't classify the upstream as dynamic), the slot is **not** marked dynamic. On subsequent executions when the shape drifts again (e.g., due to KV cache growth), the code hits the `DSP_THROW` "slot reassignment on shape drift is forbidden" error instead of gracefully reallocating. This could crash, or worse, the stale cached array with wrong shape continues being used — producing wrong results.

The same pattern appears in the fused-chain path (lines 689-726 replacing old lines 3224-3250). The old code **always** marked both head and tail as `isDynamicShape = true`. The new code only does so conditionally.

### 4. **HIGH RISK — Warmup window expanded from `executeCount_ == 0` to `executeCount_ <= 1`** (lines 689 and 1143)

**Old:** `if (executeCount_ == 0 || hasDynamicUpstream)`
**New:** `if (executeCount_ <= 1 || hasDynamicUpstream)`

This means shape reassignment is now allowed on the **first decode** step (execCount=1), not just prefill (execCount=0). Combined with #3 above (conditional isDynamicShape marking), this creates a window where:
- Prefill (exec 0): shape drift detected, slot reassigned, but NOT marked dynamic
- First decode (exec 1): shape drift detected again, slot reassigned again, still NOT marked dynamic
- Second decode (exec 2): shape drifts but `executeCount_ > 1` AND `!hasDynamicUpstream`, so DSP_THROW fires

This is a tighter window but could cause the accuracy regression if the first decode step's reassignment produces the wrong output shape.

The old code only stored the max size for later use during allocation. ### 7. **MEDIUM RISK — Max-allocation path now allocates with wrong shape** (lines 3860-3900)

**Old code:**
```cpp
maxOut = new NDArray(order, maxShape, dt);
```
Where `maxShape` was computed by scaling the last dimension.

**New code:**
```cpp
if (!slot.flags.isViewCapableOp) {
    maxOut = new NDArray(order, contigShape, dt);  // contigShape = current shape, NOT max
} else {
    maxOut = new NDArray(const_cast<LongType*>(shapeInfo), dt, true);
}
auto* maxDb = maxOut != nullptr ? maxOut->dataBuffer() : nullptr;
if (maxDb != nullptr && maxBytes > maxDb->getLenInBytes()) {
    maxDb->expand(maxBytes);
}
```

The array is allocated with `contigShape` (the **current** shape, not the max shape), then the DataBuffer is expanded to `maxBytes`. This means the NDArray's **shape metadata** says it has `currentElements` elements, but the **buffer** has capacity for `maxElements`. If a kernel writes up to `maxElements` (relying on the old behavior where the shape was scaled), it writes beyond what the shape says — or if the shape is used for bounds checking, the extra capacity is never utilized and ops that depend on the larger shape produce truncated output.

### 8. **LOW RISK — `refreshStaleViewWrappersInSegment` loop refactor** (lines 860-1000)
