## Investigation Results: Missing `syncToDevice` Causing Stale GPU Buffer Reads in DSP

### Finding 1: **NO `prepareSpecialUse` / `registerSpecialUse` in DSP slot execution** ✅ CONFIRMED GAP

`NativeDynamicShapePlan_slotexec.cpp` contains **zero calls** to `prepareSpecialUse` or `registerSpecialUse`. These are the standard CUDA coherency primitives used by every legacy NativeOps entry point (pairwise, transform, reduce, etc.) and all NDArray math operations.

**What they do:**
- `prepareSpecialUse({writes}, {reads})` → calls `syncToDevice()` on all read arrays, allocates device buffers for writes
- `registerSpecialUse({writes}, {reads})` → ticks `tickReadDevice()` / `tickWriteDevice()` actuality counters

**Impact:** Without these, the DSP path skips the systematic device coherency that the standard path gets for free.

### Finding 4: **Actuality Counter Drift — The Root Cause**

The `syncToSpecial` method (DataBuffer.cu line 792) has an early-exit guard:
```cpp
if (isSpecialActual() && !forceSync) return;  // ← skips sync if device is "current"
```

And `prepareSpecialUse` is what sets these counters via `syncToDevice()` → `tickWriteDevice()` / `tickReadDevice()`. 

**The problem chain:**
1. Slot N writes to device buffer → `tickWriteDevice()` is **NOT called** (no `registerSpecialUse`)
2. `specialActual` flag becomes stale/drifts from reality
3. Later, `syncToDevice()` is called but `syncToSpecial()` early-exits because `isSpecialActual()` returns true (wrongly)
4. GPU kernel reads stale device data

### Finding 5: **`tl_dspExecutionStream` — Stream Isolation, Not Race Condition**

The DSP stream (`tl_dspExecutionStream`) is set via RAII guards (`DspStreamGuard`) at execution entry. All `syncToSpecial` calls use this stream when available (DataBuffer.cu line 953):
```cpp
bool useDspStream = (tl_dspExecutionStream != nullptr && !switchedDevice);
cudaStream_t stream = useDspStream ? tl_dspExecutionStream : 0;
```

This is **not** a race condition between streams — the same DSP stream is used throughout a single `execute()` call. However, it means that if an external input was synced on stream 0 (e.g., by Java-side `OpaqueNDArray.fromINDArray()`), and DSP reads it on the DSP stream without an intervening sync, there could be a dependency gap. The `cudaMemcpyAsync` on the DSP stream should handle this via stream ordering, but only if `syncToDevice` is actually called.

### Summary: Root Cause

**The DSP execution path skips `prepareSpecialUse`/`registerSpecialUse` calls that the standard CUDA path relies on for device coherency.** The selective `syncToDevice` only covers data-dependent/control-input slots. For the normal flow of transformer layer ops (matmul, layernorm, attention, etc.), intermediate arrays accumulate actuality counter drift because:

1. **Producers** write to device but never call `tickWriteDevice()` 
2. **Consumers** don't call `prepareSpecialUse` → don't call `syncToDevice()` → don't verify device data is current
3. **`syncToSpecial()` early-exits** based on stale `isSpecialActual()` state

This causes small numerical errors (reading partially-stale GPU buffers) that compound through 30 transformer layers.

### Recommended Fix

Add `NDArray::prepareSpecialUse(outputs, inputs)` before `slot.ident.op->execute(&ctx)` and `NDArray::registerSpecialUse(outputs, inputs)` after, mirroring the standard legacy NativeOps pattern. This ensures all inputs are synced to device and actuality counters stay accurate.
