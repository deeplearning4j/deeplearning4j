## Analysis: `prezeroSegmentOutputs` Guard Change

### 1. What `prezeroSegmentOutputs` Does

**Definition**: `_slotexec.cpp:1421` → delegates to `platformPrezeroSegmentOutputs`

**CUDA impl** (`_slotexec_cuda.cu:45-132`): Iterates all slots in the segment and zeros output buffers for qualifying slots. Has **6 filter conditions** (lines 62-69):
- Skip `frozenConstantSlot()` 
- Skip `!needsZeroedOutput` (op fully writes its output)
- Skip `isViewCapableOp`, `isIdentityOp`, `inPlaceFused`, `isFusedChainTail`
- Skip `FROZEN + isFullyWriting` (already known to overwrite completely)

Then batches qualifying buffers into a single `launchBatchMemset` kernel call.

**CPU impl** (`_cuda_stubs.cpp:522-553`): Same filtering, uses `arr->nullify()` individually.

### 2. The Guard is Redundant AND Harmful

The guard at `_segments.cpp:931`:
```cpp
if (!(shapesFrozen_ && executeCount_ >= 2)) {
    prezeroSegmentOutputs(seg, stream);
}
```

**Redundant**: The prezero function already has internal filtering at line 69 (`_slotexec_cuda.cu`):
```cpp
if (slot.state_ >= NativeSlot::SlotState::FROZEN && slot.flags.isFullyWriting) continue;
```
For frozen steady-state slots with `isFullyWriting=true`, prezero already skips them. The guard adds nothing for these ops.

**Harmful**: The guard skips prezero for **ALL** slots, including those where `needsZeroedOutput=true` — slots the function was specifically designed to zero. This defeats the purpose of the filtering logic.

### 3. Ops in the LLM Graph with `needsZeroedOutput=true`

The flag computation (`NativeDynamicShapePlan.cpp:1096-1097`):
```cpp
slot.flags.isFullyWriting = fullyWrites && !isDataDependent && !partialWriter;
slot.flags.needsZeroedOutput = !aliasesInput && !isFullyWriting;
```

Three categories of ops in the Qwen graph get `needsZeroedOutput=true`:

| Op | Reason | Risk Level |
|---|---|---|
| `autoregressive_decode` | **Absent from OpTraitTable entirely** — no traits → `fullyWrites=false` | HIGH — 3 outputs all flagged |
| `gather` | Has `FULLY_WRITING` via `DATA_MOVE` BUT also `DATADEP` → `isFullyWriting=false` | MEDIUM — embedding lookup each step |
| `concat` | Same pattern as gather (`DATA_MOVE + DATADEP`) | LOW — depends on graph structure |

### 4. Can Skipping Prezero Leave Stale Data?

**Yes, in theory.** The flow is:
1. **Steps 0-1**: prezero runs → zeros qualifying output buffers → ops execute and write results
2. **Step 2+**: prezero SKIPPED → output buffers contain previous step's results → ops execute

For ops that **fully overwrite** their output (even if not tagged `isFullyWriting`), this is safe — the stale data is overwritten. But:

- If an op **accumulates into** its output (reductions with partial writes), the stale values corrupt the accumulation
- If a buffer is **max-allocated** (larger than actual decode shape), the op only writes `[1, hidden]` but the buffer holds `[seqLen, hidden]` from prefill — the trailing bytes are stale
- If the op **conditionally writes** some elements (scatter-like patterns), unwritten positions retain previous values instead of zeros

### 5. The All-Zero Logits Symptom

The "all-zero logits after step 2" symptom is more likely caused by a **different interaction** in the same uncommitted changeset, not directly by this guard. Here's why:

- Skipping prezero would produce **stale** data (previous step's values), not **zeros**
- For the logits to be all-zero, something must be **preventing the ops from writing** or **zeroing the buffer after the op writes**

However, there's a subtle indirect mechanism: if the `autoregressive_decode` op (which has `needsZeroedOutput=true`) depends on its output being pre-zeroed for internal accumulation logic, and the guard skips that zeroing, the op might malfunction. The op's 3 outputs (tokenIds, tokenCount, timingInfo) contain decode-loop state that might need clean initialization each invocation.

### 6. Key Architectural Observation

The **GPU backend direct-exec path** (`_gpubackend.cu:3703`) calls `prezeroSegmentOutputs` **unconditionally** — no guard. The **CUDA graph replay path** (`_cudagraph.cu:398`) intentionally skips it because memsets are captured into the graph. Only the **slot-by-slot path** (`_segments.cpp:931`) has this new guard.

This inconsistency means:
- Triton/GPU backend segments: always get prezero (**correct**)
- CUDA graph replay segments: prezero captured in graph (**correct**)  
- Slot-by-slot segments after step 2: **no prezero at all** (**potentially broken**)

### 7. Recommendation

**The guard should be removed.** The prezero function's internal filtering already handles the optimization correctly — it skips frozen fully-writing slots (the vast majority of decode ops). The outer guard adds negligible performance benefit (the function already returns quickly when all slots are filtered out) while creating correctness risk for the ~3 ops that genuinely need zeroed output buffers.

If the concern is memset overhead for the few remaining `needsZeroedOutput=true` slots, the correct fix is to add `autoregressive_decode` to the `OpTraitTable` with `OP_TRAIT_FULLY_WRITING` (if it truly overwrites all outputs), and/or to remove `DATADEP` from the `isFullyWriting` suppression for `gather`/`concat` (since data-dependence affects shape computation, not buffer write coverage).
