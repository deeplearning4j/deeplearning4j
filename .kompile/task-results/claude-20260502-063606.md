### 1. Full rms_norm_linear op implementation

- For rank > 2 inputs: reshapes `x` [B,S,K] → `x2d` [M,K] and `output` [B,S,N] → `out2d` [M,N], runs `helpers::rmsNormLinear`, then optionally copies back.

### 2. What `reshape(order, shape, false)` means

From `NDArray.hXX:3536-3573`:

- **`copyToNewBuff = true` (default, old code):** Always allocates a new buffer and copies data via `applyTransform(Assign)`. The returned NDArray is independent — writes to it are self-contained.
- **`copyToNewBuff = false` (new code):** Attempts a **zero-copy view** first. Calls `reshapeNoAlloc` to check if contiguous strides can be computed for the new shape. If YES → creates a view sharing the same `DataBuffer`. If NO (non-contiguous strides) → **falls back to copy** (`copyToNewBuff` is flipped to `true`).

### 3. The DSP regression risk — YES, this is dangerous

**The critical bug path:**

1. DSP allocates `output` as a freshly-allocated, C-contiguous [B,S,N] array (the common case for `OP_TRAIT_FULLY_WRITING` ops).
2. `output->reshape('c', {M,N}, false)` succeeds as a view — `out2d` shares `output`'s DataBuffer. `directWrite = true`.
3. `helpers::rmsNormLinear` writes to `out2d`. Because both CPU and CUDA helpers write directly to the output pointer (`bufferAsT<T>()` / `specialBuffer()`), the data lands in `output`'s buffer. **This path works correctly.**

**BUT here's the failure scenario:**

4. If `output` is somehow **non-contiguous** (e.g., from a prior DSP view operation, transpose, or permute), `reshapeNoAlloc` returns false, and `reshape('c', {M,N}, false)` **falls back to creating a fresh copy**.
5. Now `out2d->dataBuffer() != output->dataBuffer()`, so `directWrite = false`.
6. `helpers::rmsNormLinear` writes to `out2d`'s **temporary** buffer.
7. The `!directWrite` branch then tries to copy back: `out2d->reshape(output_shape, false) → output->assign(reshaped)`.

**Problem:** On CUDA, this assign-back happens **on the host-side** without proper stream synchronization. The `rmsNormLinearFusedKernel` (or the `MmulHelper::mmul` cuBLAS call) launched on the CUDA stream may not have completed when `assign` begins reading from `out2d`. The `registerSpecialUse` that would mark device data as authoritative was already called by the helper, but the assign reads from `out2d` which may have stale host data.

**However**, there's an even more fundamental issue:

### 4. The real regression: the old code always copied on reshape

The **old code** used `reshape('c', shape)` with `copyToNewBuff = true` (the default). This means:
- `x2d` was always a **copy** of `x` in 2D layout.
- `out2d` was always a **fresh allocation** in 2D layout.
- After `rmsNormLinear` wrote into `out2d`, **the data was never copied back to `output`**.

Wait — that's the pre-existing bug the new code is trying to fix! The old code wrote into a temporary `out2d` and then just deleted it without copying back, meaning `output` was **never written** for rank>2 inputs. The new code fixes this by:
1. First trying a view (so writes go directly to `output`).
2. If the view fails, explicitly copying back.

### 5. Where the new code can still regress in DSP

The `!directWrite` assign-back path has these risks:

**Risk A: CUDA stream ordering.** The `rmsNormLinear` CUDA helper calls `registerSpecialUse({output})` which marks `out2d`'s device buffer as authoritative. Then `out2d->reshape(...)` with `false` on a freshly-allocated contiguous `out2d` will succeed as a view (it's already C-contiguous). The `output->assign(reshaped)` should do a device-to-device copy. This should be safe because `assign` calls `prepareUse` which handles actuality. **Likely OK but fragile.**

**Risk B: DSP frozen shapes bypass `prepareOutputs`.** After `executeCount_ >= 3`, DSP sets `shapeFunctionOverride(true)` which skips output allocation. The output array from the context pool is reused. If this output was originally allocated as C-contiguous and the DSP slot is correctly wired, `reshape('c', {M,N}, false)` should always produce a view. **The risk is minimal in steady-state because DSP-allocated outputs for FULLY_WRITING ops are always fresh C-contiguous buffers.**

**Risk C: CPU helper mismatch.** The CPU `rmsNormLinear_` does `output->assign(&outF32)` internally when output dtype isn't FLOAT32. This means the CPU helper already handles the copy-to-output correctly for non-F32. But if `out2d` is a view of `output`, and the helper internally assigns into `out2d` (which IS `output`'s buffer), that works. If `out2d` is a copy, the helper writes to the copy, and then the op-level `!directWrite` branch copies back. **Double copy but functionally correct on CPU.**

### 5. CPU vs CUDA helper behavior

| Path | CPU | CUDA (M=1 fused) | CUDA (M>1 general) |
|------|-----|-------------------|---------------------|
| Writes to | `output->bufferAsT()` via MmulHelper (or temp if non-F32, then assign) | `output->specialBuffer()` directly via kernel | `output` via MmulHelper::mmul |
| Stream sync | N/A | Kernel writes directly, registered via `registerSpecialUse` | cuBLAS on launch stream |
| Assign-back needed? | Only if out2d != output buffer AND output is the reshaped copy | Same | Same |

### Conclusion

The new code is **fixing a real bug** (the old code was broken for rank>2 — data wrote to a temporary and was lost). But the fix has a subtle correctness issue in the `!directWrite` assign-back path:

**`out2d->reshape(output->ordering(), *outShape, false)`** — When `out2d` is a temporary (non-view), reshaping it back to [B,S,N] with `false` will succeed as a view (since `out2d` is a freshly-allocated C-contiguous buffer). Then `output->assign(reshaped)` copies from reshaped → output. On CUDA, this requires proper stream synchronization between the `rmsNormLinear` kernel and the assign. The helper already calls `registerSpecialUse`, so `out2d`'s device buffer is marked authoritative, and `assign`'s `prepareUse` should handle the sync correctly.

**Net assessment:** The code should be functionally correct but adds unnecessary overhead. A simpler fix would be:
- If `directWrite` is false, just do `output->assign(out2d)` directly — no need for the intermediate reshape, since `out2d` [M,N] and `output` [B,S,N] have the same total elements and assign handles shape broadcasting/striding.
