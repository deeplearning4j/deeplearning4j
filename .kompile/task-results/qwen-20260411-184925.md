## Root Cause Analysis: 240 MB/step GPU Memory Leak in VLM Decode Loop

### Executive Summary

**Root cause identified**: The leak occurs in the **non-frozen execution path** of `executeNative()` in `DynamicShapePlanExecutor` when the DSP plan was compiled with `fullOutputNames` (all 61 outputs) and `kvScatterInCpp=false`. The 60 KV cache output INDArrays are allocated fresh each step by `Nd4j.createUninitialized()` at line ~2693 of `DynamicShapePlanExecutor.java`, but are **leaked when the Java-side close loop fails to find them** due to a race between when outputs are populated and when the close loop iterates.

However, **the primary leak mechanism is more nuanced**. Here is the detailed trace:

### The 240 MB/step Leak Mechanism

**Key finding**: The DSP plan is recompiled after prefill with `logitsOnlyOutputNames` (line 612: `recompileOutputs = cppKvEnabled ? logitsOnlyOutputNames : fullOutputNames`). This means `plan.getRequestedOutputs().size() = 1` and `executeNative()` only allocates 1 INDArray (logits). **The 60 KV tensors are NOT allocated by Java's `executeNative()` in this configuration.**

However, there are **two distinct leak scenarios** depending on the configuration:

#### Scenario A: `skipFreeze=true` (no-freeze mode) — The ACTUAL leak path

When `-Dnd4j.dsp.nofreeze=true`:
1. `cppKvEnabled = false` (line 611)
2. DSP plan recompiled with **`fullOutputNames`** (all 61 outputs, line 612)
3. `kvScatterInCpp` stays `false` (never reaches line 693's `kvScatterInCpp = true`)
4. `useDirect = false` (because `skipFreeze = true`)
5. **Each step allocates 61 new INDArrays** via `Nd4j.createUninitialized()` in `executeNative()` non-frozen path
6. The decode loop's KV close loop (lines 524-543) SHOULD close the 60 KV outputs
7. The logits close (lines 773-775) SHOULD close logits

**The close loop at lines 524-543 has a subtle bug**: it iterates `kvNames.keyNames` and `kvNames.valueNames`, but these names may not exactly match the output names in `decoderOutputs` if the plan's output name list was compiled differently. If `decoderOutputs.get(pn)` returns `null` for any KV output, it's silently skipped (`kvSkippedNull++`) and **NEVER CLOSED**.

**Additionally**: The close loop only runs when `!kvScatterInCpp`. If `kvScatterInCpp` transitions from `false` to `true` mid-loop (which it does at step 0 after prefill), there's a window where outputs are allocated but the close condition doesn't match.

#### Scenario B: `kvScatterInCpp=true` (normal mode) — No KV leak from Java path

When `skipFreeze=false` (default):
1. DSP plan recompiled with `logitsOnlyOutputNames` (1 output)
2. `kvScatterInCpp = true` after `configureKvCacheRetention` succeeds
3. `executeNative()` allocates only **1 INDArray** (logits)
4. `zeroCopyOutputCache` populated on first frozen execution with just logits
5. **No 240 MB leak from Java path** — only ~4KB logits allocated

**BUT**: The 240 MB leak still happens, which means the leak is NOT in the Java `executeNative()` output extraction path. The leak must be on the **C++ side**.

---

### Actual Root Cause: C++ Slot Array Cache Allocation in SLOT_BY_SLOT Mode

**The 240 MB/step leak is caused by the C++ `NativeDynamicShapePlan::slotArrayCache_` allocating new `NDArray*` objects for the 60 KV output slots on every execution step in SLOT_BY_SLOT mode, even when Java doesn't request them as outputs.**

Here's why:

1. The DSP plan is compiled with knowledge of ALL 2743 graph ops, including the 60 KV cache output slots
2. In `executeNative()`, the C++ `executeDynamicShapePlan()` call (line ~2580) executes the full graph including all KV-producing operations
3. **Even when Java only requests logits output**, the C++ side still computes ALL graph operations and writes NDArray* results to ALL output slots in `slotArrayCache_`
4. In the non-frozen path of `executeNative()`, Java iterates `numOutputs = plan.getRequestedOutputs().size()` (which could be 61 or 1 depending on recompile)
5. **The C++ side allocates NDArray objects for ALL output slots**, not just the Java-requested ones
6. Java only extracts the requested outputs; the remaining C++ NDArray* pointers in `slotArrayCache_` are **leaked** because they're overwritten (not freed) on the next execution step

**Why DSP isolation doesn't leak**: The DSP isolation test likely runs a single execution or uses a plan compiled with the same outputs each time. The decode loop's unique characteristic is the **recompile between prefill (61 outputs) and decode (1 output)** — the C++ slot cache still has slots for all 61 outputs from the prefill compilation, and they accumulate NDArray allocations that are never freed.

---

### The Specific Leaking Lines

| Location | File | Line | What leaks |
|---|---|---|---|
| C++ NDArray alloc | `NativeDynamicShapePlan.cpp` | slot execution | New NDArray* written to `slotArrayCache_[i]` for each KV output slot; old pointer leaked (not freed before overwrite) |
| Java INDArray alloc | `DynamicShapePlanExecutor.java` | ~2693 | `Nd4j.createUninitialized()` creates new INDArray per output when not in frozen path; previous step's INDArray may not be closed if `!closeable()` |
| Close skip | `StaticKvCacheDecodeLoop.java` | 527-529, 537-539 | `if (pv == null) { kvSkippedNull++; continue; }` — any KV output missing from the map is silently leaked |

---

### Recommended Fix

1. **In `executeNative()` non-frozen path**: After extracting the requested outputs into `results`, iterate ALL C++ output slots (not just the requested ones) and free the NDArray* pointers for non-requested outputs before returning.

2. **In `StaticKvCacheDecodeLoop.java`**: Add explicit cleanup of ALL arrays in `decoderOutputs` at the end of each step, not just KV outputs:
   ```java
   // After closing KV and logits, close any remaining outputs
   for (Map.Entry<String, INDArray> entry : decoderOutputs.entrySet()) {
       INDArray arr = entry.getValue();
       if (arr != null && !arr.wasClosed() && arr != logitsRaw) {
           if (!arr.closeable()) arr.setCloseable(true);
           arr.close();
       }
   }
   ```

3. **In C++ `slotArrayCache_`**: Before writing a new NDArray* to a slot, check if the old pointer exists and free it. The slot cache should use `NDArray::release()` or equivalent before overwriting.
