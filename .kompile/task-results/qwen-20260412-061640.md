### 2. Identified Stale Data Survival Paths

#### PATH A: `frozenSkipNullify` skips zeroing of non-fully-overwriting ops

**Location**: `NativeDynamicShapePlan_slotexec.cpp`, lines 1371-1398

```cpp
bool frozenSkipNullify = shapesFrozen_ && executeCount_ >= 2;
// ...
if (frozenSkipNullify && !slot.flags.needsZeroedOutput) continue;  // SKIP nullify
```

**Condition**: When `shapesFrozen_` is true AND `executeCount_ >= 2`, any op whose `SlotFlags::needsZeroedOutput == false` will have its output buffer **NOT nullified** before execution.

**Stale data mechanism**: If an op does NOT fully overwrite its output buffer (partial write, conditional write, data-dependent output size), the leftover data from the previous decode step persists. This is especially dangerous for:
- **Attention score matrices** with sequence-length-dependent dimensions
- **TopK/argmax outputs** where the number of valid tokens changes between steps
- **Any op that writes fewer elements than the buffer capacity**

The `needsZeroedOutput` flag is set at compile time based on op classification. If an op is incorrectly classified as "fully overwriting" when it sometimes doesn't, stale data leaks through.

#### PATH B: `writeOutputSlot()` frees old arrays only if NOT referenced elsewhere — view aliasing blind spot

**Location**: `NativeDynamicShapePlan.cpp`, lines 306-339

```cpp
bool referencedElsewhere = false;
for (int i = 0; i < totalOutputSlots_; i++) {
  if (i != slotIdx && outputSlots_[i] == old) {
    referencedElsewhere = true;
    break;
  }
}
if (!referencedElsewhere) {
  planOwnedArrays_.erase(old);
  delete old;
}
```

**Condition**: When `writeOutputSlot()` is called with `old != value`, it checks if the OLD NDArray pointer appears in any OTHER slot. If not, it deletes it.

**Stale data mechanism**: This check only catches **exact NDArray pointer aliasing across slots**. It does NOT detect:
- Two NDArray objects that share the **same underlying DataBuffer** but have different NDArray wrappers (e.g., different shape/stride metadata pointing to the same GPU memory)
- Views created from the same source buffer via `createView()` that have separate NDArray objects

If a downstream op's input is a view of an upstream op's output buffer, and the upstream op's output gets freed+reallocated, the downstream op's view still points to the freed memory.

**`validateReusableSlotArray` checks** (lines 931-956):

**CRITICAL MISSING CHECK**: There is **NO content zeroing** on the `cached2` reuse path. If the op doesn't fully overwrite the buffer, stale data from the previous step survives. The validation is purely structural (is the buffer valid, not closed, has proper device allocation).

**Condition**: Since commit `89d1f28925`, `slotArrayCache_` IS `outputSlots_` (via `#define`). Therefore `slotArrayCache_ != outputSlots_` is **always false**, and the `oldCached` deletion block is **dead code**.

**Stale data mechanism**: Before unification, this code would delete a stale cached array that was different from the new output. After unification, this path is permanently disabled. The deletion now relies entirely on `writeOutputSlot()` (PATH A above), but `writeOutputSlot()` only deletes if the old array is plan-owned and not referenced elsewhere. If the old array is a view or was created by a different mechanism, it may survive.

#### PATH E: Graph replay writes directly to pre-allocated buffers — no slot execution at all

**Location**: `NativeDynamicShapePlan_gpubackend.cpp` (direct replay path) and `NativeDynamicShapePlan_cudagraph.cu` (CUDA graph replay)

When a segment has a valid replay handle (`seg.exec.replayHandle->replay(stream)`), the entire segment executes as a captured CUDA graph. The graph writes directly to the GPU buffers that were captured during the capture step.

**Condition**: If the captured graph's output buffers were allocated with specific sizes during capture, and a subsequent decode step has **different effective tensor sizes** (even if shapes are "frozen", dynamic elements like KV cache position could affect how much of the buffer is valid), the graph writes only to the captured-size portion. Any buffer beyond the written region retains stale data.

Additionally, **graph replay does NOT go through slot execution** — it never calls `writeOutputSlot()` or nullifies. The `outputSlots_[slotIdx]` entries still point to the same NDArray objects from capture time. If those NDArray objects' DataBuffers were replaced between steps (which shouldn't happen in frozen mode, but could due to a bug elsewhere), the graph writes to the wrong buffer.

The buffer contents are never updated.

### 3. Most Likely Root Cause for VLM Decode Garbage

The convergence of **PATH A** (frozenSkipNullify) + **PATH C** (cached2 reuse without zeroing) + **PATH D** (dead oldCached deletion code) creates the most plausible stale data vector:

1. During decode step N, an op produces output in a buffer of shape `[1, vocab_size]`
2. The op doesn't have `needsZeroedOutput=true`, so it's assumed to fully overwrite
3. At decode step N+1 (`executeCount_ >= 2`):
   - `frozenSkipNullify` prevents `nullify()` of the output buffer
   - The `cached2` reuse path returns the same buffer without zeroing
   - The op executes but writes only a **partial** result (e.g., due to dynamic token count, attention mask length, or KV cache position)
   - The unwritten portion of the buffer contains **garbage from step N**
4. This garbage propagates through the decode pipeline as attention scores or logits

**The unification of `slotArrayCache_` with `outputSlots_` (commit 89d1f28925) is the catalyst** because:
- The `oldCached != nullptr && slotArrayCache_ != outputSlots_` guard at line 1437 is now permanently false
- The safety valve that would have deleted and reallocated stale cached arrays is permanently disabled
- Every slot now shares a single storage location — any bug that causes a slot to retain a stale NDArray object has no fallback
