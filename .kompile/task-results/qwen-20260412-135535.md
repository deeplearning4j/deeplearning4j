## Investigation Results: DSP Fastpath vs Standard Path Divergence

### 1. Full Execution Path for Fastpath Mode (`DeclarableOp::execute()`)

The execution sequence is:

```
execute(Context*) 
  → validateDataTypes()       // validates input/output types match
  → prepareOutputs()          // allocates/validates output arrays
    → if (shapeFunctionOverride && isFastPath): EARLY RETURN (skip shape inference + allocation)
    → else: calculateOutputShape() → allocate output if needed
  → KernelDispatchHelper::dispatchWithAutoTune()  // try helper (e.g., FlashAttentionHelper)
  → validateAndExecute()      // calls op's executeOp() if no helper found
```

**Key finding for `prepareOutputs()`**: When `shapeFunctionOverride=true` (DSP mode), the function returns immediately at line 410, skipping **all** shape inference and output allocation. The standard path (`shapeFunctionOverride=false`) runs `calculateOutputShape()` and validates/allocates outputs. Both paths reach the actual `executeOp()` with `fastpath_out()` populated — but the **properties of those output arrays differ**.

### 2. Output Array Reallocation — **LIKELY ROOT CAUSE for matmul**

**Standard path** (`shapeFunctionOverride=false`):
- `prepareOutputs()` calls `calculateOutputShape()` which runs the op's shape function
- For matmul, the shape function declares: `zOrder = xOrder == 'c' && yOrder == 'c' ? 'c' : 'f'`
- If output doesn't exist, it creates: `new NDArray(out, true, ctx.launchContext())` where `out` is the shapeInfo from the shape function (preserving the declared ordering and strides)

**DSP path** (`shapeFunctionOverride=true`):
- Skips `prepareOutputs()` entirely
- Output arrays are pre-allocated by DSP's slot execution code using the shape function's declared ordering
- **However**, the strides are computed from scratch by `ShapeBuilders::createShapeInfo()` which calls `shape::updateStrides(shapeInfo, order, false)`

**Critical issue**: The matmul shape function declares ordering but the **strides embedded in the shapeInfo** from the shape function may differ from what `ShapeBuilders::createShapeInfo()` generates. The shape function returns a `ConstantShapeHelper::getInstance().createShapeInfo(...)` which may have different stride computation than the standard path's `shape::updateStrides()`.

**More critically for matmul/cuBLAS**: In `MmulHelper.cu` `mmulMxM()`, cuBLAS dispatch depends on the output array's **actual strides**, not just its declared ordering:

```cpp
bool cMcont = M == 1 || C->strideAt(0) == 1;
bool cNcont = N == 1 || C->strideAt(1) == 1;
```

If DSP provides an output with strides that don't match what cuBLAS expects (e.g., the output was allocated with a stride computation mismatch), cuBLAS would write data assuming wrong memory layout, producing corrupted output.

### 3. Matmul/cuBLAS Stride Dependency — **CONFIRMED**

**Yes, cuBLAS dispatch is stride-dependent.** In `MmulHelper.cu` (`mmulMxM`, lines ~940-1090):

1. **Contiguity checks** use actual stride values (`strideAt(0)`, `strideAt(1)`)
2. **Non-contiguous outputs get dup'd to Fortran order**: `if (!cMcont) { pC = C->dup('f'); }`
3. **Leading dimension** `ldc` is computed from actual stride: `const int ldc = (cMcont && cNcont) ? M : pC->strideAt(1);`
4. **After cuBLAS call, if dup'd, results are assigned back**: `if (C != pC) C->assign(pC);`

If the DSP-preallocated output has different strides than the standard path's allocated output, the `cMcont`/`cNcont` checks may differ, leading to:
- Different transpose decisions
- Different `ldc` values passed to cuBLAS
- Different memory access patterns

**The `assign()` back path** should theoretically handle this, but if there's a subtle bug in how `assign()` handles stride mismatches or the dup'd temporary has different properties, this could cause divergence.

### 4. `onnx_multi_head_attention` — Temporary Arrays and Output Pre-reading — **CONFIRMED RISK**

The op **does read from output arrays before writing to them** in the past-KV concat path (lines 171-211):

```cpp
auto presentKeyOut = block.outputWidth() > 1 ? OUTPUT_VARIABLE(1) : nullptr;
kFinal = presentKeyOut->permute(permBHSDtoBSHD, false, false);  // VIEW into output
NDArray* kPastSlice = (*kFinal)(pastSliceIdx);                   // SLICE of output
kPastSlice->assign(pastKeyBSHD);                                 // WRITE to output
```

The `permute(..., false, false)` creates a **view** (no copy) into the output buffer. Then `slice()` creates another view. If the output buffer contains **stale data** from a previous execution (which DSP reuses across warmup→decode transitions), and the slice/assign doesn't fully overwrite the region, stale data could leak through.

However, this affects `present_key`/`present_value` outputs (indices 1 and 2), **not** the main `output` (index 0). The main output goes through `FlashAttentionHelper::forward()` which fully writes it.

**More concerning**: The `AttentionWorkspace` reuses buffers across calls (`attnOut4d` obtained via `AttentionWorkspace::getBuffer()`). If the workspace buffer contains stale data from a previous shape and the write is partial, this could corrupt the attention output.

### 5. VariableSpace Dependency — **NOT the cause**

The `onnx_multi_head_attention` op **does not call `getVariableSpace()`** anywhere. It only uses `INPUT_VARIABLE()`, `OUTPUT_VARIABLE()`, `INT_ARG()`, `T_ARG()`, and `block.width()`/`block.outputWidth()` — all of which work correctly in fastpath mode.

However, `DeclarableOp::getZ()` does check `ctx.getVariableSpace()` in the non-fastpath branch. Since both DSP and standard paths use fastpath (`isFastPath()=true`), this code path is never hit for either.

### 6. `isInplace()` Flag — **NOT the cause**

Both DSP and standard paths have `isInplace=false` for this op. DSP creates contexts as `new Context(1)` (which sets `_isInplace=false`), and the standard path sets it from `op.isInplaceCall()` which is `false` for `onnx_multi_head_attention`. The `isInplace` flag doesn't affect execution for this op.

## Most Likely Root Causes (ranked)

1. **Stride/ordering mismatch in matmul output** (highest probability). DSP pre-allocates outputs with strides computed via `ShapeBuilders::createShapeInfo()`, while the standard path uses `shape::updateStrides()`. If these produce different stride values for the same shape+ordering, cuBLAS in `mmulMxM()` would compute different `lda`/`ldb`/`ldc` values and write data in a different layout. The `assign()` back should normalize this, but if the intermediate dup'd array (`pC`) has different properties, subtle corruption could occur.

2. **AttentionWorkspace stale buffer**. The `AttentionWorkspace` caches `attnOut4d` by key. If the key doesn't fully encode the shape/configuration, a buffer from a previous execution with different dimensions could be reused, containing stale data that isn't fully overwritten.

3. **CUDA graph capture vs replay address mismatch**. `MmulHelper.cu` has explicit handling for `tl_graphExecutionActive` (line ~1277). If DSP uses CUDA graphs and the standard path doesn't, or if the graph was captured with different array addresses than replay, the cached cuBLAS Lt epilogue state or cast cache could use wrong pointers.
