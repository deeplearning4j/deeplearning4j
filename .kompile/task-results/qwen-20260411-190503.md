## ROOT CAUSE ANALYSIS: 256 MB/step GPU Memory Leak

### The Leak Mechanism — Two-Part Failure

The 256 MB/step leak comes from **non-capturable segments executing slot-by-slot during `phaseReplay()`**, combined with the **pre-exec allocation path in `executeSegmentWithGpuGraph()`**. Here's the exact chain:

---

### Part 1: Non-Capturable Segments Allocate Intermediates Every Step

**File:** `NativeDynamicShapePlan.cpp` → `phaseReplay()` (line 1838)  
**File:** `NativeDynamicShapePlan_segments.cpp` → `executeSegmentSlotBySlot()` (line 785)  
**File:** `NativeDynamicShapePlan_slotexec.cpp` → `executeSlot()` (line 878)

During `phaseReplay()`, segments that are NOT captured as graphs (`useGraph = false`) execute via `executeSegmentSlotBySlot()`. Every slot in those segments runs `executeSlot()`, which at `step3_allocate:` (line ~2056) does:

```cpp
NDArray* cached = validateReusableSlotArray(slotIdx, slotArrayCache_[slotIdx], "step3-reuse-validate");
if (cached != nullptr) {
  // reuse if shape+dtype match
}
// else: allocate new
```

**This path correctly reuses arrays when shapes are frozen and match.** No leak here.

### Part 2: GPU Backend's Pre-Exec Allocation — THE TRUE LEAK

**File:** `NativeDynamicShapePlan_gpubackend.cpp`  
**Function:** `executeSegmentWithGpuGraph()`  
**Lines:** ~2217-2340

Here's the critical code path:

```cpp
// Line ~2217: Skip optimization during stable frozen replay
if (!(shapesFrozen_ && seg.exec.executionCount > 2 && seg.exec.replayHandle != nullptr)) {
  for (int stepIdx = seg.def.startSlot; stepIdx <= seg.def.endSlot; stepIdx++) {
    // ... validate input DataBuffers ...
    
    for (int i = 0; i < slot.wiring.numOutputs; i++) {
      int slotIdx = slot.wiring.outputSlotIndices[i];
      if (outputSlots_[slotIdx] == nullptr) {
        // Allocate from cached shape info
        auto* arr = new NDArray(order, shapeVec, dt);
        outputSlots_[slotIdx] = arr;   // OVERWRITES null
        // slotArrayCache_ == outputSlots_ (macro alias), so also updated
        preExecAllocCount++;
      }
    }
  }
}
```

**THE BUG:** When `outputSlots_[slotIdx]` is `nullptr` at the start of a step, a NEW NDArray is allocated. On the NEXT step, `outputSlots_[slotIdx]` is non-null (it was just set), so the code does NOT allocate a new one — it finds the existing one and reuses it.

**BUT:** If ANY code path between steps sets `outputSlots_[slotIdx]` back to `nullptr`, the next step allocates again, orphaning the previous step's allocation.

### Part 3: What Nulls the Slots Between Steps?

The `releaseGpuIntermediates()` function (line 2040) has this code at line ~2125:

```cpp
// First pass: null out all VIEW_OF_SLOT entries
for (int i = 0; i < totalOutputSlots_; i++) {
  if (outputSlots_[i] != nullptr &&
      slotOwnership_[i].ownership == BufferOwnership::VIEW_OF_SLOT) {
    outputSlots_[i] = nullptr;   // <-- NULLS the slot
    slotOwnership_[i].reset();
  }
}
// Second pass: free SLOT_OWNED buffers
for (int i = 0; i < totalOutputSlots_; i++) {
  if (outputSlots_[i] != nullptr &&
      slotOwnership_[i].ownership == BufferOwnership::SLOT_OWNED) {
    // ... free the array ...
    outputSlots_[i] = nullptr;   // <-- NULLS the slot
  }
}
```

**If `releaseGpuIntermediates()` is called between decode steps**, it nulls ALL intermediate slots and frees their arrays. The next step's pre-exec allocation path then allocates brand new arrays for every null slot. **2743 ops × ~96KB average = ~256 MB.**

### Part 4: Why `cudaMemPoolTrimTo` Only Recovers 32 MB

Because `releaseGpuIntermediates()` does `delete` the old NDArrays, which triggers `DataBuffer` deallocation. The CUDA memory pool gets the freed memory back. BUT the pre-exec allocation immediately re-allocates 256 MB worth of new arrays. `cudaMemPoolTrimTo` can only trim memory that is currently free — most of the 256 MB is actively held by the newly allocated arrays. The 32 MB recovered is the difference (fragmentation, metadata, etc.).

### The Leak Summary

| Step | What Happens | GPU Memory Impact |
|------|-------------|-------------------|
| 1. `execute()` runs | Allocates 256 MB for 2743 slot arrays | +256 MB |
| 2. `releaseGpuIntermediates()` called | Frees slot arrays, nulls `outputSlots_[]` | -224 MB (returned to pool) |
| 3. Next `execute()` | Pre-exec alloc re-creates 256 MB of arrays | +256 MB |
| 4. `cudaMemPoolTrimTo` | Trims only the freed-but-unused portion | -32 MB recovered |
| **Net per cycle** | **Leak = 256 MB** | **Never freed** |

### The Fix

**The fix depends on the intended behavior:**

1. **If `releaseGpuIntermediates()` should NOT be called between decode steps:** The caller (Java `StaticKvCacheDecodeLoop`) should NOT call it, or should call `releaseGpuIntermediates(true /* preserveDecodeState */)` instead. With `preserveDecodeState=true`, nothing is freed (line 2220-2235 returns 0 immediately).

2. **If `releaseGpuIntermediates()` MUST be called between steps:** The pre-exec allocation loop in `executeSegmentWithGpuGraph()` (line ~2217) should NOT re-allocate arrays that were intentionally freed. Instead, `outputSlots_[]` should be preserved (not nulled) by `releaseGpuIntermediates()`. The fix would be to add a flag like `preserveSlotArrays` that skips the nulling pass.

3. **If the slot arrays should persist across steps (the intended design per the "one array per slot" comments):** `releaseGpuIntermediates()` should NOT null `outputSlots_[i]` for slots that have invariant shapes. The code at line ~1290 in `execute()` says: "One array per slot: NO cleanup between executions. Same plan = same shapes. Arrays allocated on first execution, reused forever." Calling `releaseGpuIntermediates()` between steps directly contradicts this design.

**The most likely correct fix: Option 1** — ensure `releaseGpuIntermediates()` is either not called between decode steps, or called with `preserveDecodeState=true`. The "one array per slot, reused forever" design is correct for frozen-shape decode, and `releaseGpuIntermediates()` with `preserveDecodeState=false` fundamentally breaks it.
