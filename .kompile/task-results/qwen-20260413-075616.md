### 1. FROZEN EXECUTION PATH — Major Changes

Java allocates new placeholder arrays each step, so their pointers always change. Including them made the address key never match, keeping the plan permanently stuck at `SHAPES_FROZEN` — never advancing to `POINTERS_STABLE` or `REPLAYING`.
- Same exclusion applied to the CUDA version in `NativeDynamicShapePlan_cudagraph.cu`.

**⚠️ VIEW_RECIPE_FAIL risk:** Skipping `prepareSpecialUse`/`registerSpecialUse` means input arrays may have stale GPU data and output actuality counters won't be ticked, causing **compounding errors** through the decoder. The commit message acknowledges this but claims "all data is already device-resident and actuality flags are correct" — this is only true if the previous step's GPU writes completed. If there's a cross-stream timing issue, data will be stale.

### 4. ROOT CAUSE ANALYSIS FOR 305 VIEW_RECIPE_FAIL ERRORS

**Most likely causes:**

1. **`af8a42b409` — Skipped `prepareSpecialUse`/`registerSpecialUse`**: This is the #1 suspect. These calls handle GPU↔CPU data synchronization and actuality counter updates. Skipping them means:
   - Input arrays may have stale GPU data from the previous step
   - Output actuality counters aren't ticked, causing downstream ops to think their inputs haven't changed
   - **Compounding errors** through the decoder graph (each wrong output poisons the next op)

2. **`7ff51ae45c` — Permute view stride fix**: If the permutation source array (input[1]) isn't properly synced to host before reading (`permArr->syncToHost()`), the permutation values could be garbage, producing wrong view strides. This directly maps to VIEW_RECIPE_FAIL — the view recipe (shape+strides) is wrong.

3. **`7ff51ae45c` — Frozen nullify skip**: Skipping nullify for ops without `needsZeroedOutput` flag. If an op's `needsZeroedOutput` flag is incorrectly set to false when it actually needs zeroing, the output buffer would contain stale data from the previous step.

4. **Dead constant passthrough** (`7ff51ae45c`): Changed from creating zeros for closed DataBuffers to passing the original array through. If the GPU memory was actually freed (not just marked closed on Java side), this would cause the native plan to read from freed memory.

### 5. STALE DATA RISK IN GRAPH REPLAY

The combination of changes in `af8a42b409` and `7ff51ae45c` creates a potential stale data scenario:

- **Skip sync** → GPU data may not be current
- **Skip nullify** → Output buffers retain previous step's data
- **Actuality counters not ticked** → Downstream ops don't know inputs changed
- **Permutation from device array** → If sync fails, wrong strides

The `DynamicShapePlanExecutor` Java-side stride matching (`createUninitialized(dtype, shape, strides, ordering)` + dup-to-contiguous safety net) is a good defensive measure but can't fix wrong data that was already computed on the C++ side with wrong strides.
