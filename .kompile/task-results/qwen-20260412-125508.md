### 7. **FROZEN execution path: `nullify()` logic changed — adds `needsZeroedOutput` skip condition** (slotexec.cpp, ~lines 1362-1400 in current)

**Before (old code, line ~1443):**
```cpp
if (!slot.inPlaceFused) {
  // ... view check ...
  if (!isBatchZeroActive() && !shouldPreserveWarmupOutputsDuringCapture()) {
    ctxOuts[i]->nullify();  // ALWAYS nullify
  }

```

**After (new code, line ~1371):**
```cpp

  // ... same view check ...
  if (!isBatchZeroActive() && !shouldPreserveWarmupOutputsDuringCapture()) {
    if (frozenSkipNullify && !slot.flags.needsZeroedOutput) continue;  // NEW: skip nullify
    ctxOuts[i]->nullify();
  }
}
```

**Behavioral impact:** **HIGH — THIS IS VERY LIKELY THE BUG.**

In frozen steady-state execution (`shapesFrozen_ && executeCount_ >= 2`), outputs are now **NOT nullified** unless `slot.flags.needsZeroedOutput` is `true`. The old code always nullified all non-view outputs before re-execution.

This means: if an op previously relied on the output buffer being nullified before execution (e.g., partial writes, conditional writes, or ops that use the existing buffer contents), the old buffer contents are now preserved. The op may read stale data from the previous execution and produce wrong results.

Specifically for ops that do **OVERWRITE_RESULT** — most ops set this flag and fully overwrite their output, so skipping nullify is fine. BUT if any op does NOT fully overwrite and instead partially writes (e.g., scatter, conditional select, or certain reduction patterns), the stale data would corrupt the result.

**This is the most likely root cause of wrong output (token 'L' instead of '<').** The `needsZeroedOutput` flag may be incorrectly set for some op, or an op may partially write its output expecting the buffer to start zeroed.
