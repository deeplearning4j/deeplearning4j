## Final Analysis: Ops at Risk for Stale Buffer Bug

### Candidate 1: **`reshape_no_copy`** (674 instances) — **HIGH RISK**

**Traits:** `VIEW = OP_TRAIT_VIEW_PRODUCING | OP_TRAIT_VALUE_DEPENDENT_SHAPE`
**`needsZeroedOutput`:** `false` (because `isViewCapableOp = true`)

**The bug:** `reshape_no_copy` at lines 38-49 only writes to output when `output->dataBuffer() != input->dataBuffer()`. When the buffers ARE the same (output reuses a buffer previously used by a different op), the op returns without writing anything. Since `needsZeroedOutput = false`, the frozen fast-path skips nullify, and the `cached2` path skips nullify entirely. **Stale data from the previous use of this buffer bleeds through.**

Additionally, the op at line 27-29 returns early if shapes are identical (no-op), again without writing to the output buffer.

### Candidate 2: **`gather`** (365 instances) — **MEDIUM RISK (correctly classified but vulnerable in cached2 path)**

**Traits:** `GATHER = DATA_MOVEMENT | VALUE_DEPENDENT_SHAPE | GATHER`
**`needsZeroedOutput`:** `true` ✅ (correct — NOT view-capable, NOT fully-writing)

The trait is correctly set. However, in the `cached2` reuse path (slotexec.cpp:2210-2215), even `needsZeroedOutput` is not checked — there's no nullify at all. If a gather op goes through the cached2 path (max-allocation reuse), its output buffer is reused without zeroing. The gather kernel writes exactly `numIndices * TAD_size` elements. If the buffer was previously larger, stale tail data persists.

**BUT:** The NDArray's shapeInfo is set to the correct (smaller) shape, so downstream ops should only read the logical portion. This is only a problem if:
- Shape inference gives a larger shape than the actual data written
- The buffer is later reinterpreted with a different shape that includes the stale tail

### Candidate 4: **`expand_dims`** (190 instances) — **MEDIUM RISK**

**Traits:** `VIEW = OP_TRAIT_VIEW_PRODUCING | OP_TRAIT_VALUE_DEPENDENT_SHAPE`
**`needsZeroedOutput`:** `false`

`expand_dims` adds a dimension of size 1. It's a view-producing op that shares the input buffer. If the output buffer is NOT a view (fresh allocation), the op needs to copy data from input to output. If the output buffer contains stale data and isn't zeroed, and the op only copies a portion of the data (e.g., when strides change), stale data could bleed through.

However, `expand_dims` typically creates a view (sharing the input buffer), so the `isViewCapableOp` flag should prevent the nullify skip from being harmful in most cases.

### Candidate 5: **`reshape`** (674 instances) — **MEDIUM RISK**

**Traits:** `VIEW = OP_TRAIT_VIEW_PRODUCING | OP_TRAIT_VALUE_DEPENDENT_SHAPE`
**`needsZeroedOutput`:** `false`

Same concern as `reshape_no_copy` but with a different implementation. The regular `reshape` may also skip writing when the buffer is shared.

### The `cached2` Path Gap — **SYSTEMIC RISK**

**File:** `libnd4j/include/graph/impl/NativeDynamicShapePlan_slotexec.cpp`, lines 2210-2215

The `cached2` reuse path has **zero zeroing** for ANY op. This is a systemic gap:
- `cached` reuse (line 2104-2123): nullifies for non-view-capable ops ✅
- `cached2` reuse (line 2210-2215): **never nullifies** ❌

Any op that goes through the max-alloc → cached2 path with `needsZeroedOutput = false` risks stale data. This includes:
- All view-capable ops (reshape, reshape_no_copy, expand_dims) — but they may share buffers, so the "stale" data is actually the input data
- All fully-writing ops (matmul, concat, cast, equals, create) — they fully overwrite, so no risk
- **Ops that are NOT fully-writing but not view-capable** — this is the gap

Looking at the trait table, the ops in the decoder that are NOT fully-writing AND NOT view-capable:
- **None in the explicit list** — all data movement ops (`gather`, `concat`, `stack`, `split`, `slice`, `tile`, `scatter_nd`) have either `FULLY_WRITING` or `VIEW_PRODUCING` set

But wait — let me re-check `gather`:
- `GATHER = DATA_MOVE_VALDEP | OP_TRAIT_GATHER`
- `DATA_MOVE_VALDEP = DATA_MOVE | VALUE_DEPENDENT_SHAPE`
- `DATA_MOVE = DATA_MOVEMENT | FULLY_WRITING`

So `gather` = `DATA_MOVEMENT | FULLY_WRITING | VALUE_DEPENDENT_SHAPE | GATHER`. It IS marked as `FULLY_WRITING`!

This means `gather` has `needsZeroedOutput = false` (fully-writing, not view-capable, not data-dependent).

**But the gather kernel writes only `numIndices` elements, not the full buffer.** If the buffer was max-allocated larger than the actual output shape, the gather kernel won't fill the entire buffer. However, the NDArray's shapeInfo correctly reflects the smaller shape, so downstream consumers read the right amount.

**The actual risk comes when:** the same NDArray buffer is used by a subsequent decode step where the shape grows. The cached buffer from step N (small shape) is reused for step N+1 (larger shape), and the tail from step N's data is stale.

## Summary: Likely Culprits Ranked

### **1. `reshape_no_copy` — PRIMARY SUSPECT**
- **674 instances** in the decoder
- `needsZeroedOutput = false` (view-capable)
- **Does NOT write to output** when input/output share the same buffer (line 38-49 returns early)
- When the output buffer was previously used by a different op, stale data persists
- The op is supposed to create a view (share buffer), but when that's not possible (different buffer), it copies — but only if `input->lengthOf() == output->lengthOf()`. If shapes differ, it's a silent no-op.

### **2. `cached2` reuse path — SYSTEMIC BUG**
- Lines 2210-2215: zero nullify for ANY op
- Affects all ops that go through the max-allocation reuse path
- Should at minimum check `slot.flags.needsZeroedOutput` and nullify when true

### **3. `gather` — SECONDARY SUSPECT**
- **365 instances**
- Marked as `FULLY_WRITING` in the trait table, which sets `needsZeroedOutput = false`
- The kernel writes exactly `numIndices * TAD_size` elements
- If the allocated buffer is larger than the logical output, tail data is stale
- Combined with the `cached2` path gap, stale tail data can persist across decode steps

### **4. `expand_dims` / `reshape` — TERTIARY**
- View-capable, so `needsZeroedOutput = false`
- May not write to output buffer when buffer-sharing conditions aren't met
- Risk is lower if they consistently create proper views
