### **CRITICAL FINDING: Non-Deterministic Set Iteration**

**The root cause is in `ForwardExecutionDAGBuilder.findConstants()` / `findVariables()` / `findPlaceholders()`:**

```java
// Line 654-676 in ForwardExecutionDAGBuilder.java
private Set<String> findConstants() {
    return sameDiff.getVariables().values().stream()
        .filter(v -> v.getVariable().getVariableType() == VariableType.CONSTANT)
        .map(v -> v.getVariable().name())
        .collect(Collectors.toSet());  // ← RETURNS HashSet (NO ORDERING GUARANTEE)

```

**The problem:**
1. `sameDiff.variables` is a `PatriciaTrie` (iterates in **lexicographic order**)
2. `Collectors.toSet()` creates a **`HashSet`** with **no iteration order guarantee**
3. The `HashSet` iteration order can vary between JVM runs, different hash seeds, or even different memory layouts

### **Why This Causes Wrong Computation**

**Within a single compilation + execution cycle, the ordering is internally consistent:**
- Compiler builds `externalInputKeys[]` and `externalIndexMap` together
- Compiler wires slot inputs using indices from `externalIndexMap`
- Executor reads `plan.getExternalInputKeys()` and populates `extInputs[i]` in array order
- C++ deserializes external input names in the same order from the serialized plan

**BUT if the plan is compiled once and reused:**
- The HashSet iteration order is **fixed at DAG construction time**
- The plan's `externalInputKeys[]` array is serialized with that order
- C++ deserializes and expects `externalInputs[0]` = first name in the array, etc.

**The actual bug scenario:**
If the DAG is rebuilt (e.g., after session reset, model reload, or graph modification), the `findConstants()` etc. methods are called again, potentially producing a **different HashSet iteration order**. This would assign different indices to the same constants, causing:
- Index 5 that was `"weight_layer_1"` becomes `"bias_layer_23"`
- The model computes with wrong weight matrices
- Results diverge gradually as wrong constants accumulate errors

### **The Fix**

**Replace `Collectors.toSet()` with `Collectors.toCollection(LinkedHashSet::new)` to preserve PatriciaTrie's lexicographic iteration order:**

```java
// In ForwardExecutionDAGBuilder.java, lines 654-676:
private Set<String> findConstants() {
    return sameDiff.getVariables().values().stream()
        .filter(v -> v.getVariable().getVariableType() == VariableType.CONSTANT)
        .map(v -> v.getVariable().name())
        .collect(Collectors.toCollection(LinkedHashSet::new));  // ← PRESERVE ORDER
}

private Set<String> findVariables() {
    return sameDiff.getVariables().values().stream()
        .filter(v -> v.getVariable().getVariableType() == VariableType.VARIABLE)
        .map(v -> v.getVariable().name())
        .collect(Collectors.toCollection(LinkedHashSet::new));  // ← PRESERVE ORDER
}

private Set<String> findPlaceholders(Set<String> requiredVariables) {
    return requiredVariables.stream()
        .filter(varName -> {
            Variable var = sameDiff.getVariables().get(varName);
            return var != null && var.getVariable().getVariableType() == VariableType.PLACEHOLDER;
        })
        .collect(Collectors.toCollection(LinkedHashSet::new));  // ← PRESERVE ORDER
}
```

This ensures **deterministic, reproducible ordering** across DAG rebuilds while preserving the PatriciaTrie's natural lexicographic order.
