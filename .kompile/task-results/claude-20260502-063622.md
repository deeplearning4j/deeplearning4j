### Finding 1: `markExternalInputVariable` + `invalidateForRebuild` resets executeCount but NOT `compilationDone_`

**Severity: HIGH**
**Location:** `DspSegmentLifecycle.h:147-178`, `NativeDynamicShapePlan.h:1603`

The `invalidateForRebuild` function (called by `markExternalInputVariable`) resets:
- `executeCount_ = 0` (via `resetExecuteCount()`)
- `frozenConstantDetectionDone_ = false`
- All segment execution state

But it does **NOT** reset:
- `compilationDone_` — stays `true`
- `pointersStable_` — set to `false` by `markExternalInputVariable`

After invalidation, `executeCount_ == 0` + `shapesFrozen_ == true` → `isFirstFrozenWarmup = true` → dispatches to `phaseWarmup()`. Warmup re-executes all slots. **This path looks correct.**

But the `compilationDone_` gap matters: after warmup completes and `executeCount_` increments to 1, the next execution at `executeCount_ == 1` skips `phaseCompile` (line 1933: `if (!compilationDone_ && ...)` — `compilationDone_` is still `true`). This means stale compiled backends from before the invalidation are reused. If those backends have baked-in addresses that are now invalid due to staging buffer reallocation, they would execute with stale pointers.

### Finding 2: `phaseShapeInferenceOnly` allocates zero-initialized arrays that persist through warmup

**Severity: MEDIUM (not the primary cause for decode, but could cause prefill issues)**
**Location:** `NativeDynamicShapePlan.cpp:3751-3754`

```cpp
NDArray* outArr = new NDArray(const_cast<LongType*>(siOutputShapes[i]), true);
outputSlots_[slotIdx] = outArr;
```

The pre-pass creates `NDArray(shapeInfo, true)` — this allocates a buffer but does NOT compute values. The buffer content is whatever `cudaMalloc` returns (often zeros on CUDA due to ECC memory clearing, but **not guaranteed**).

For the frozen/decode path, this is irrelevant because `shapePrePassDone_` is guarded by `!shapesFrozen_` at line 1883. But for the **unfrozen prefill path**, the pre-pass runs before the first slot-by-slot execution. Warmup then clears shape caches (line 2984-2986) but does NOT delete the zero-initialized arrays from `outputSlots_[]`. The slot-by-slot execution should overwrite them — BUT if any slot hits a shape cache match (stale from pre-pass) and skips re-execution, those zeros persist.

### Finding 3 (MOST CRITICAL): `silu` in-place corruption in `llm_ops.cpp`

**Severity: CRITICAL**
**Location:** `llm_ops.cpp:309-321`

```cpp
// OLD (working):
input->applyTransform(transform::Sigmoid, output);
output->applyPairwiseTransform(pairwise::Multiply, input, output);

// NEW:
if (output->buffer() == x->buffer()) {
    NDArray* sigmoid = input->transform(transform::Sigmoid);
    output->applyPairwiseTransform(pairwise::Multiply, sigmoid, output);
    delete sigmoid;
} else {
    input->applyTransform(transform::Sigmoid, output);
    output->applyPairwiseTransform(pairwise::Multiply, input, output);
}
```

**The in-place path has a bug:** When `output == input` (in-place), it computes `sigmoid = sigmoid(x)` (correct), then does `output = output * sigmoid = x * sigmoid(x)` (correct on first read). **BUT on CUDA, the `buffer()` check uses HOST pointers** while the actual computation uses device pointers. If `isPrimaryActual() == false` (host buffer not synced), `buffer()` might return a pointer that doesn't match even for in-place operations, causing the wrong branch to execute.

More critically: the in-place check `output->buffer() == x->buffer()` compares **primary (host) buffer pointers**. On CUDA, the `CONFIGURABLE_OP_IMPL(silu, 1, 1, true, ...)` has `true` for in-place, meaning `output` IS `input`. But `buffer()` returns the host pointer, and after DSP frozen execution, many arrays have `isPrimaryActual() == false` (only device buffer exists). In this state, `buffer()` may return a stale or null host pointer, and the comparison could fail even when the arrays share the same device buffer.

### Finding 5: `rms_norm_linear` reshape changes

**Severity: MEDIUM**
**Location:** `llm_ops.cpp:1110-1122`

```cpp
// OLD: auto x2d = x->reshape('c', xShape2d);
// NEW: auto x2d = x->reshape('c', xShape2d, false);
```

The `false` parameter to `reshape` means "don't copy data if reshape requires it." If the input is non-contiguous (e.g., a view), this could create a zero-copy view that shares the buffer — but with `false`, if the reshape is not possible without a copy, it returns a **null or incorrect view**. This could silently produce zeros.

### Recommended Investigation Priority

1. **`silu` / `swish_mul` in-place detection** (`llm_ops.cpp`) — Most likely root cause. These are called on every token in the LLM decode path. If the in-place branch misfires on CUDA, `sigmoid(x)` overwrites `x` before the multiply, producing `sigmoid(x) * sigmoid(x)` instead of `x * sigmoid(x)`. For large values this approaches 1.0, for negative values approaches 0.0. The net effect: output values are crushed toward 0 and 1, which after many layers could produce all-zero logits.

2. **`markExternalInputVariable` not resetting `compilationDone_`** — Could cause stale compiled backends to execute with wrong addresses after segment invalidation.

3. **`rms_norm_linear` reshape with `false`** — Could silently produce wrong results for non-contiguous inputs.

4. **`phaseShapeInferenceOnly` zero-initialized arrays** — Lower priority since the frozen path guard prevents this from running during decode.
