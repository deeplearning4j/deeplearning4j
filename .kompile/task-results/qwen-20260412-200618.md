## Findings: Decode Loop KV Cache Management Investigation

### Summary

The `<doctag>upsupsupsup...` pattern (correct first token, then degenerate repetition) is a classic symptom of the **KV cache not being updated** — the model keeps attending to the same KV state from prefill on every decode step. After tracing the full decode path, I've identified **three specific failure points** that could cause this.

---

### Finding 1: **The causal mask in padded mode is built ONCE and never updated** (MOST LIKELY CAUSE)

**Location:** `DecoderUtils.java`, lines 737-746 (the `isCausalMask` branch in `buildDecoderInputMap`)

In padded mode (`usePadded = true`), the causal mask is allocated once on the first decode step and cached in `reusableInputs`:

```java
if (canReuse && reusableInputs.containsKey(inputName)) {
    decoderInputMap.put(inputName, reusableInputs.get(inputName));  // REUSES SAME ARRAY
} else {
    long totalSeqLen = maxKvLen + currentSeqLen;
    INDArray causalMask = buildCausalMask(currentSeqLen, totalSeqLen);
    decoderInputMap.put(inputName, causalMask);
    if (canReuse) reusableInputs.put(inputName, causalMask);
}
```

**The bug:** Unlike the `attention_mask` (LONG mask) which is **updated in-place** each step:
```java
// attention_mask branch - DOES update:
if (cachePos > 0) {
    mask.get(NDArrayIndex.point(0), NDArrayIndex.interval(0, cachePos)).assign(1);
}
mask.putScalar(0, totalSeqLen - 1, 1);
```

...and unlike the `attn_mask_reformat` (FLOAT bias) which **also updates in-place**:
```java
// attn_mask_reformat branch - DOES update:
if (cachePos > 0) {
    for (int p = 0; p < (int) cachePos; p++) {
        bias.putScalar(new long[]{0, 0, 0, p}, 0.0f);
    }
}
```

**The causal mask branch does NO in-place update on reuse.** It just passes the same cached array through unchanged. The mask was built on the **first decode step** (step 1 after prefill) with a specific `totalSeqLen = maxKvLen + 1` pattern, and every subsequent step reuses that exact same mask data.

While the causal mask for decode (currentSeqLen=1) is all-zeros (the model attends to all positions), this mask has the shape `[1, 1, 1, maxKvLen+1]` and the **data is correct for any decode step** (all zeros means "attend to everything"). So the causal mask itself may not be the direct cause of degeneration — but see Finding 2.

### Finding 2: **The `attn_mask_reformat` bias update only unmask past positions, but doesn't re-mask stale positions** (LIKELY CONTRIBUTING FACTOR)

**Location:** `DecoderUtils.java`, lines 819-832

The `attn_mask_reformat` bias is updated each step:
```java
if (cachePos > 0) {
    for (int p = 0; p < (int) cachePos; p++) {
        bias.putScalar(new long[]{0, 0, 0, p}, 0.0f);  // Unmask positions [0, cachePos)
    }
}
```

**The problem:** This only sets positions `[0, cachePos)` to `0.0` (attend). But it does **NOT re-mask** positions `[cachePos, maxKvLen)` back to `MASK_FILL`. After the first decode step:
- Step 1: cachePos=prefillLen. Sets [0, prefillLen) → 0.0. Positions [prefillLen, maxKvLen) are MASK_FILL (from initial build). **Correct.**
- Step 2: cachePos=prefillLen+1. Sets [0, prefillLen+1) → 0.0. Position prefillLen was already 0.0 from step 1, and the rest is still MASK_FILL. **Still correct (cumulative).**

This is actually fine because the updates are cumulative (positions only go from masked→unmasked, never the reverse). So this is **NOT the root cause**.

### Finding 3: **The KV scatter writes to `cachePos` but the attention reads from the CONCAT of past_key + current_key** (ROOT CAUSE — THE PERMUTE FIX INTERACTION)

**This is the most likely root cause.** Here's the chain of events:

1. **Prefill completes.** Present KV outputs are `[1, heads, prefillLen, dim]`. Java's `padKvCacheToStaticSize` copies this into static buffers `[1, heads, maxKvLen, dim]` at positions `[0:prefillLen]`. `cachePosition` = prefillLen.

2. **DSP recompiles with static KV shapes.** `configureKvCacheRetention` maps present outputs → past input buffers. `kvScatterInCpp = true`.

3. **Decode step 1:** 
   - `pastSeqLen` (from attention code) = `effectiveKArr->sizeAt(2)` = **prefillLen** (correct, from static KV buffer).
   - `seqKVCur` = 1 (current token).
   - Attention attends over `seqK = prefillLen + 1` positions.
   - **BUT** the effective key/value is derived from the **past_key input** which is the full static buffer `[1, heads, maxKvLen, dim]`. The attention code at line 2409 says:
     ```cpp
     pastSeqLen = static_cast<int>(effectiveKArr->sizeAt(2));  // = maxKvLen, NOT prefillLen!
     ```
   
   **WAIT** — this is the critical issue. In padded mode, the past_key is the **full static buffer** with shape `[1, heads, maxKvLen, dim]`, NOT a view. So `pastSeqLen = maxKvLen`, not `prefillLen`.

   **This means `seqK = maxKvLen + 1`** — the attention attends over the entire static buffer (including zero-padded positions), not just the valid prefix.

4. **The attention mask/bias is supposed to mask out the zero-padded positions** `[prefillLen, maxKvLen)`. This is done via the `attn_mask_reformat` bias input. On the first decode step, this bias correctly masks positions `[prefillLen, maxKvLen)` to `MASK_FILL`.

5. **KV scatter writes new token's KV to position `cachePos` (= prefillLen) in the static buffer.** This happens in `scatterKvEntries()` at line 2430:
   ```cpp
   entry.cachePos = kvCachePosition_;  // = prefillLen
   ```

6. **Here's where it breaks:** After the scatter, position `cachePos` has valid data. But on the **next decode step**, `cachePos` increments to `prefillLen + 1`, and the scatter writes to position `prefillLen + 1`. However:

   **The permute fix we applied may have changed the strides of the present_key/present_value outputs.** If the present KV output from the attention op now has different memory layout (e.g., non-contiguous due to a transpose/permute), the `kvScatterBatchedKernel` does a raw `memcpy`-style copy:
   ```cpp
   for (LongType d = threadIdx.x; d < e.dim; d += blockDim.x) {
       dst[dstOffset + d] = src[srcOffset + d];  // Assumes contiguous!
   }
   ```
   
   If `src` (present KV) is **not contiguous** (strided due to permute), this copy reads wrong memory. The scattered KV data would be garbage, and the model would attend to corrupted KV state.

### Finding 4: **`pastSeqLen` derivation in the attention may be wrong for padded static KV** (CONFIRMED ISSUE)

In `TritonIRBuilder_module.cpp` line 2409:
```cpp
pastSeqLen = static_cast<int>(effectiveKArr->sizeAt(2));
```

In padded mode, `effectiveKArr` is the **full static buffer** with `sizeAt(2) = maxKvLen`. So `pastSeqLen = maxKvLen` (e.g., 935 for a 256-token prefill with maxKvLen=1191). 

But the **valid** KV data only occupies positions `[0, cachePos)`. The attention kernel attends over `seqK = maxKvLen + 1` positions, relying on the bias mask to block invalid positions. This works IF the bias mask is correct.

**However**, `seqKVCur` is derived as:
```cpp
NDArray* curKArr = resolveArr(kSrc);
seqKVCur = (curKArr && curKArr->rankOf() == 3) ? static_cast<int>(curKArr->sizeAt(1)) : 1;
```

If `kSrc` in padded mode is also derived from the static buffer (or a view of it), `seqKVCur` could be wrong.

**Actually this is fine for the single-token decode case** — `seqKVCur = 1` is correct.

### Finding 5: **The Java-side `cachePosition` counter and C++ `kvCachePosition_` may diverge** (POSSIBLE)

In `StaticKvCacheDecodeLoop.java` line 541:
```java
kvCacheManager.setCachePosition(kvCacheManager.getCachePosition() + 1);
```

And line 545:
```java
decoderDspExec.syncSavedKvPosition(kvCacheManager.getCachePosition());
```

But the C++ side at `NativeDynamicShapePlan.cpp` line 1346:
```cpp
scatterKvEntries(externalInputs, numExternalInputs, stream);
kvCachePosition_++;
```

The C++ increments `kvCachePosition_` AFTER scatter. The Java increments its counter BEFORE the C++ has finished. If there's a timing/race issue, the Java's `cachePos` (used to build attention_mask and position_ids) could be one ahead of the C++'s `kvCachePosition_` (used for scatter writes).

**Actually, looking more carefully, this is synchronized:** Java reads `cachePos` at the **start** of each step (line 414), which is the value from the **previous** step's scatter. The Java increment happens at line 541, which is after the current step's scatter. So the sequencing is:
- Step N starts: `cachePos = N` (from step N-1's increment)
- Step N executes: C++ scatters to position `kvCachePosition_ = N`, then increments to `N+1`
- Java syncs: `setCachePosition(N+1)`
- Step N+1 starts: `cachePos = N+1` ✓

This is correct — **NOT the root cause**.

### CONCLUSION: Most Likely Root Cause

**Finding 3 (stride mismatch from permute fix) is the most likely root cause.** The pattern `<doctag>upsupsupsup...` means:
1. First token (`<doctag>`) is generated correctly — this comes from the prefill KV state which is valid.
2. Subsequent tokens degenerate — the KV scatter is writing **corrupted data** into the static buffer, so each decode step attends to garbage KV.

**Specifically:** If the permute fix changed the present_key/present_value output to be non-contiguous (strided), the `kvScatterBatchedKernel` reads wrong data because it assumes contiguous `[dim]` elements. The scattered KV contains incorrect values, causing the model to produce degenerate output.
