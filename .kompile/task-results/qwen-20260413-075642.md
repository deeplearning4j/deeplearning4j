### Commits Most Likely to Cause Stale Data Reads

#### 1. `634fabf1b7` — Remove stale `tl_graphExecutionActive` (Apr 11) ⚠️ **MOST LIKELY CULPRIT FOR RECENT REGRESSIONS**

**What changed:** `tl_graphExecutionActive` was being set to `true` during ALL backend segment execution in `NativeDynamicShapePlan_segments.cpp:677`, not just during CUDA graph capture. This flag controls `DataBuffer::syncToSpecial()` — when set, it creates pinned host copies of device data.

**Stale data mechanism:** During normal Triton execution (not graph capture), this flag being true caused `syncToSpecial()` to create stale pinned host copies. On replay, the replay read from the pinned host copy instead of the current device buffer → wrong output.

**Fix:** Removed `tl_graphExecutionActive=true/false` from `executeSegmentWithSpecificBackend`. Also added `compilationDone_` flag to prevent re-compilation during replay.

---

#### 2. `af8a42b409` — Fix phase transition address key (Apr 13, today) ⚠️ **MOST RECENT**

**What changed:** `computeSegmentInputAddrKey` and `computeSegmentInputAddrKeyPortable` were hashing external input buffer addresses (Java-allocated placeholder arrays). Java allocates new arrays each decode step, so these addresses always changed, making `argTableStable` stay `false` forever. The plan got stuck at `SHAPES_FROZEN`, never advancing to `POINTERS_STABLE` or `REPLAYING`.

**Stale data mechanism:** Without phase advancement, the plan never reached the graph replay path. External inputs were synced every step via the slow path, but the arg table (which the captured graph's H2D memcpy nodes read from) never got marked stable. This means either: (a) graph replay never happened at all, or (b) graph replay used arg table addresses from an earlier step that didn't match current buffers.

**Fix:** External inputs (srcIdx < 0) are now excluded from the address key hash. Only cross-segment internal buffer addresses are hashed.

#### 3. `2fac9dfdbb` — Guard warmup array deletion during capture (Apr 1)

**What changed:** Added `!tl_graphExecutionActive` guards at 6 NDArray deletion sites in `slotexec.cpp`. Without this, warmup arrays saved in `savedWarmupOutputSlots` were deleted during capture → `WARMUP_RESTORE` restored dangling pointers → use-after-free → corrupted DataBuffer.

**Stale data mechanism:** Use-after-free of warmup arrays means the restored output slots pointed to freed memory. Any replay reading from those slots got garbage.

**Stale data mechanism:** Without FROZEN promotion, slots bypassed the frozen fast path and went through normal execution, which includes sync paths that can create stale buffers.
